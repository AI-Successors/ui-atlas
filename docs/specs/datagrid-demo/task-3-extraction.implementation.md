# Task 3: table exploration implementation

Status: authorized implementation. Governing [requirements](task-3-extraction.requirements.md).

## Approach

Extend the current public mapper inspector and reuse the bounded acquisition service from the public peer worktree. Keep all changes in this task's worktree. Retain the existing public literal-text reader; do not introduce a provider, dependency, or private source.

1. Add an explicit image-exploration acquisition mode. Validate table/header geometry and pixel joins in this mode without claiming OCR qualification. Existing MappingSurvey/FreshRead retain their reading gate.
2. Add read-only preparation from the clicked candidate: seal the current target and candidate rectangle, identify the header/body regions and physical structure, and discover available scrolling. Use UIA scroll support where available and sealed native-host scrolling otherwise. Unknown support fails closed with a useful result.
3. Use the existing bounded observe/move/observe service for traversal, receipts, cancellation, unique pixel registration, coverage, and safe restoration. Never derive pixel displacement from scrollbar percentages or cell text. Reject disconnected or ambiguous captures.
4. Assemble accepted header/body regions at their verified offsets into a bounded original-resolution PNG, plus table/header geometry. Validate source hashes and exclude mapper UI. Retain incomplete coverage as partial and show the reason.
5. Update the floating inspector with Ready, Exploring, Result, and failure states. One Explore action, Stop while running, and an image preview with a single Show structure control and Save image. Expose no axis choices. Show the brief bounds/restore explanation before Explore. Keep inspector progress outside the capture region during the run.
6. Wire cancellation, selection lifetime, passive refresh, foreground checks, and recorder coordination. A recorder cannot issue concurrent input. Capture scopes must hide owned decorations without hiding the Stop control for the entire run.

## Cross-display theme refresh correction

The recorder panel and mapper overlay previously created separate STA dispatchers; the table inspector belonged to the overlay dispatcher. Loading Fluent resources in the recorder registers its window in WPF's process-wide themed-window collection. WPF's system-settings message handler calls `ThemeManager.OnSystemThemeChanged`, which accesses those windows on the receiving dispatcher. A message delivered to the mapper dispatcher therefore accessed the recorder window from the wrong thread. A regression test on the installed .NET Windows Desktop 10.0.12 runtime reproduced the reported `Dispatcher.VerifyAccess` / `ThemeManager.OnSystemThemeChanged` exception before the correction. The relevant upstream paths are [ThemeManager](https://github.com/dotnet/wpf/blob/v10.0.0/src/Microsoft.DotNet.Wpf/src/PresentationFramework/System/Windows/ThemeManager.cs) and [SystemResources](https://github.com/dotnet/wpf/blob/v10.0.0/src/Microsoft.DotNet.Wpf/src/PresentationFramework/System/Windows/SystemResources.cs).

`RecorderUiDispatcher` now owns the recorder, overlay, legend, inspector, and schema review on one process-lifetime STA dispatcher. Closing an individual window stops its timers without terminating the shared dispatcher. Queued component callbacks are discarded after that component closes. Fluent styling and per-monitor DPI awareness remain enabled; no global exception handler suppresses the failure.

All three new regression cases passed: system-settings refresh with actual recorder/mapper windows and close/reopen in both orders. A separate fixture process using the CLI's per-monitor-v2 manifest moved the actual inspector across all three available displays and back. It observed native DPI **192, 120, 120, 192** (200%, 125%, 125%, 200%) and two WPF DPI-change events, with successful theme refreshes at each position. This used synthetic target content and did not operate a customer application. The standard test runner remained system-DPI aware, so its successful window moves alone were not treated as mixed-DPI evidence. Before/after regression reports and the per-monitor fixture output are retained under ignored `artifacts/dpi-theme/`.

Final Release solution and Debug CLI builds passed with zero warnings/errors. ## Vertical exploration and Azure header reading

The three latest failed application captures stopped during the first upward row movement, before establishing the origin. Native vertical position moved by one unit while the visible rows moved by 26.25 image pixels. The header remained fixed. At 125% scaling the integer-only matcher rejected the overlap; the top selected row also changed its foreground, fill, and font when the record moved away. This is an image-registration failure, separate from the local OCR misreadings in schema review.

Image exploration now uses fractional vertical registration with the same filtered comparison and unique-overlap rules as horizontal exploration. A bounded leading selection band is excluded from both comparison sides only when both observations show the same dark full-width fill and extent. Remaining body detail must establish a unique displacement; the fixed header cannot prove vertical motion. Original source pixels remain untouched. Fractional Y displacement accumulates before integer tile placement. MappingSurvey and FreshRead keep their stricter existing path. Replaying all three failed pairs through the production matcher now accepts the unique -26.25-pixel translation. This replay does not claim a fresh full application traversal; the existing duration, movement, and tile limits still apply.

Restoration skips axes already at the original position and restores vertical before horizontal, accommodating controls that reset the horizontal position when changing rows. If an exact-position command is ignored, one inverse line command is allowed only when a recorded line movement directly connects the current native state to the original state. It never assumes native units are pixels or that every line has a fixed size. Safety checks, budgets, native position verification, and pixel-anchor verification remain required. Longer unsupported restoration paths still report failure.

Recorder More → Settings and schema review's Header reading settings now select Local OCR or Azure OpenAI GPT-5.6 Sol. Light uses `reasoning.effort: low`; the configurable model value is the user's Azure deployment name. Endpoint normalization accepts the resource origin or the documented v1 suffix and constructs the Responses URL once. The endpoint/deployment are local JSON and the key is stored separately in Windows Credential Manager, scoped to the endpoint. Test connection sends a synthetic header and checks the actual reported model and returned label. Saving configuration performs no remote request. Local OCR remains the default.

Azure extraction sends the selected header-cell PNGs with fixed physical column keys, in bounded batches. Strict structured output preserves literal duplicate, blank, and unreadable names. Responses must contain every supplied key exactly once, a supported model identity, completed output, and valid status/text combinations. Any refused, malformed, incomplete, mismatched, cancelled, or failed batch rejects the whole read without silently falling back. Returned labels cannot change column geometry, source identity, capture coverage, or restoration. The reviewed artifact records the reader profile. HTTP redirects are disabled and error messages do not expose response bodies. Requests use `store: false`; service retention policies still apply.

API references: [Azure Responses](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/responses), [GPT-5.6 Sol](https://developers.openai.com/api/docs/models/gpt-5.6-sol), and [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs). Repository networking checks retain a narrow exception for this adapter and its mocked HTTP tests. Privacy documentation describes the explicit cloud option.
